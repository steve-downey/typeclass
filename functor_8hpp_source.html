32// Functor pattern invariants:
33// - Instances are single lookup objects that provide fmap(F, T).
34// - replace is a derived object operation implemented from fmap.
35// - Dispatch happens through a provided object or functor<Concrete>.
36// - Keep lookup explicit through typeclass objects, not ADL overloads.

41template <class Impl>
42struct derive_functor : protected Impl {
44 template <class FUNCTION, class T>
45 constexpr auto fmap(this auto &&self, FUNCTION &&function, T &&value)
46 requires requires(const Impl &impl) {
47 impl.fmap(std::forward<FUNCTION>(function), std::forward<T>(value));
48 }
49 {
50 return impl_of(self).fmap(std::forward<FUNCTION>(function),
51 std::forward<T>(value));
52 }

58 template <class T, class U>
59 constexpr auto replace(this auto &&self, T &&value, U &&replacement)
60 requires requires(const Impl &impl) {
61 impl.replace(std::forward<T>(value), std::forward<U>(replacement));
62 } || requires(const Impl &impl) {
63 impl.fmap(
64 detail::constant_function<std::remove_cvref_t<U>>{
65 std::forward<U>(replacement)},
66 std::forward<T>(value));
67 }
68 {
69 if constexpr (requires {
70 impl_of(self).replace(std::forward<T>(value),
71 std::forward<U>(replacement));
72 }) {
73 return impl_of(self).replace(std::forward<T>(value),
74 std::forward<U>(replacement));
75 } else {
76 // One-way derivation (not a mutually-derivable pair): route
77 // through self, not Impl, so a shadow on a wrapping Map is
78 // still reached.
79 return self.fmap(
80 detail::constant_function<std::remove_cvref_t<U>>{
81 std::forward<U>(replacement)},
82 std::forward<T>(value));
83 }
84 }
85
86 private:
88 template <class SELF>
89 static constexpr decltype(auto) impl_of(SELF &&self) {
90 return static_cast<impl_ref_t<Impl, SELF>>(self);
91 }
92};

101// -- Operation objects --
102//
103// This comment is the reference for the operation objects; the other
104// typeclass headers point back to it. The rulings are
105// docs/transpose/decisions.md#operation-objects, #lookup-variable-naming and
106// #empty-predicate-name.
107//
108// A fourth lookup mode, on top of implicit lookup, explicit object argument,
109// and NTTP pinning (examples/transpose/lookup_modes_example.cpp): the operation
110// as an object that does the lookup itself. `fmap(f, v)` names the operation
111// the caller means, rather than the object the operation is reached through.
112//
113// Two cases motivate them. First, everything-is-local code -- a container on
114// the stack that one algorithm maps or traverses -- where naming a lookup
115// object costs a line to save nothing. Second, and the reason the pattern is
116// not merely cosmetic: a *non-template* caller can not carry the typeclass as
117// an NTTP, because there is no template parameter list to hang it on. The
118// operation object resolves the instance at the call site instead.
119//
120// They are NOT customization points, and D3200R0's case for a bundled
121// mechanism depends on the difference. Customization happens once, at
122// functor<T> and its siblings. There is no per-operation hook, no
123// ADL path in, and nothing specializable that would make `fmap` mean
124// something other than what the instance's own fmap means. The familiar name
125// for this shape is "customization point object"; it is the wrong name here,
126// and these are operation objects over a customizable bundle.
127//
128// Shape, uniform across every typeclass: deduce the type that keys the lookup
129// from one designated argument, default a trailing `const auto &TC` NTTP to
130// the lookup for that type, and call through it.
131//
132// ONE NAMESPACE FOR THE WHOLE FAMILY. Every typeclass operation lives in one
133// namespace, not one namespace per typeclass. Here that namespace is
134// beman::transpose, which is already nested and already scoped to exactly
135// this facility; the standard spelling this maps to is `std::typeclass`.
136//
137// The reason is coherence, and it is part of the design rather than a
138// consequence of it. A name in here means one thing across the entire family:
139// `fmap` is Functor's map whichever instance supplies it, and Applicative is
140// free to provide the Functor names because they can not mean anything else.
141// That commitment is already load-bearing elsewhere -- it is what lets an
142// algorithm inherit from two typeclass instances at once and call both
143// unqualified (see examples/transpose/algorithm_object_example.cpp). Collecting
144// the operations in one namespace makes the commitment checkable in one place.
145// A namespace per typeclass would let `fmap` mean two things and hide it.
146//
147// It also keeps the operations away from std, where `empty`, `length`,
148// `invoke`, `to_vector`, `any_of` and `all_of` all exist with related
149// meanings. `beman::transpose::empty` is not something a caller drags into
150// scope by accident, and `std::typeclass::empty` would not be either.
151//
152// NAMING. The lookup variables get the plain names -- `functor<T>`,
153// `applicative<T>`, `foldable<T>`, `traversable<T>`, `monad<T>` -- because
154// they are the user-facing surface. What that collides with gets the longer,
155// more descriptive name: the CRTP bases became `derive_functor<Impl>` and
156// friends, which says what they do (derive the rest of a typeclass from an
157// instance's primitives) instead of relying on a capital letter to tell
158// `Functor` from `functor`.
159//
160// One consequence worth knowing: a local named `applicative` now shadows
161// `applicative<T>`. Locals holding a looked-up instance are spelled
162// `applicative_map` here, matching the existing `traversable_map` and
163// `monad_map` parameter names.
164//
165// The one name where coherence is under real strain is `empty`, which means
166// Foldable's "holds nothing" here and Alternative's "identity of alt" in the
167// sibling compile-time-scheme tree. Adding Alternative would claim it twice,
168// in the one namespace whose job is to make that impossible. That is the
169// ordinary C++ trouble with a short name in a widely-used namespace, and the
170// name is provisional like every other name here, more so than most. The three
171// languages with both typeclasses all give `empty` to Alternative and name
172// the Foldable predicate something else -- `null` in Haskell (Data.Foldable)
173// and PureScript (which re-exports Control.Plus's `empty` from the same
174// module, so the split is load-bearing there), `isEmpty` in Cats, whose
175// Alternative gets `empty` from MonoidK.
176//
177// C++ points the other way: std::empty, std::ranges::empty and every
178// container's .empty() are the *predicate*, and the language has no
179// nullary-constructor-named-empty convention to protect. So the plan here is
180// the opposite of the FP convention and consistent with the host language:
181// Foldable keeps `empty`, and Alternative's identity takes another name when
182// it arrives. `zero<C>()` sits naturally beside `pure<C>(v)` -- both build a
183// context and both must name it, for the same reason.
184//
185// PINNING is mode 2, unchanged: `tc.fmap(f, v)` on an instance object, which
186// is shorter than any spelling routed through these objects. An operation
187// object takes no explicit template arguments, so mode 3 is not available on
188// it -- the trailing TC above is reachable only as
189// `fmap.operator()<F, T, TC>(...)`, which is a curiosity, not an
190// API. The earlier lookup modes are all untouched; `typeclass` is an addition.
191
