6// Applicative and Monad instances for std::expected<T, E>.
7//
8// THREE CORES, MUTUALLY EXCLUSIVE BY CONSTRAINT.
9//
10// The same-error core handles operands that all declare this instance's error
11// type, and deduces exactly what it always did: expected<T,E>, with no
12// error_set in the carrier spelling. The same-error-plus-bare core keeps that
13// spelling when ungraded operands participate. The graded core handles real
14// mixing -- operands declaring different model grades -- and deduces their
15// join. The constraints are complements, so the choice is never a matter of
16// overload ranking (docs/transpose/decisions.md#grading-footprint).
17//
18// Every combination the graded core accepts was ILL-FORMED before grading:
19// there was no instance that would take operands with differing error types.
20// So grading claims only previously-ill-formed territory, and nothing that
21// deduced a type before deduces a different one now. The golden tests in
22// tests/beman/transpose/baseline_deduction.test.cpp are where that claim is
23// mechanized rather than argued.
24//
25// The CARRIER SPELLING is lazy. `grade_of<std::expected<T,E>>` is the
26// singleton grade `error_set<E>`, but operands that agree on an alternative
27// carry that alternative verbatim, so unmixed pipelines never acquire a
28// singleton error_set in their deduced type. A bare operand is lifted to the
29// model bottom at a mixing point and leaves no trace in the carrier spelling.
30// An error_set only appears where genuinely different alternatives met.
31//
32// Short-circuit semantics, first error wins, operands examined left to right.
33// That order is observable and therefore part of the contract, per the
34// Traversable rules in docs/transpose/CODING_RULES.md and the normative
35// left-to-right order of docs/transpose/decisions.md#applicative-objects. Note
36// that the grade is order-blind while the observed error is not: ∪ commutes, so
37// operand order cannot change the deduced type, only which error you get back.

236// -- The accumulating applicative instance ---------------------------------
237//
238// The second NTTP-pinned object over the SAME carrier and grade algebra as
239// expected_applicative_map above, per
240// docs/transpose/decisions.md#applicative-objects. Stage accumulating-object of
241// docs/transpose/transpose-grading-plan.md.
242//
243// Where the short-circuit object above keeps only the LEFTMOST failing
244// operand's witness, this object COMBINES every failing operand's witness
245// through the grade model's evidence-combine hook. Same-type collisions keep
246// the leftmost witness; model evidence with multiple slots can preserve
247// failures of genuinely different types. That is the whole difference:
248// examining every operand instead of stopping at the first.
249//
250// Structurally this mirrors expected_applicative_impl's ungraded/graded split
251// exactly -- same two constraints, same complementary coverage, same
252// bare-operand promotion. Only the failure-collecting step differs.
253
254namespace detail {

261template <class ERROR, class EXTRACT, class... OPERANDS>
262constexpr auto accumulate_failures(EXTRACT &&extract,
263 const OPERANDS &...operands)
264 -> std::optional<ERROR> {
265 std::optional<ERROR> accumulated;
266 auto fold_in = [&accumulated, &extract](const auto &operand) {
267 auto this_one = extract(operand);
268 if (!this_one.has_value()) {
269 return;
270 }
271 if (accumulated.has_value()) {
272 accumulated = combine_grade_evidence(*accumulated, *this_one);
273 } else {
274 accumulated = std::move(this_one);
275 }
276 };
277 (fold_in(operands), ...);
278 return accumulated;
279}
